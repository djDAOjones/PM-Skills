Act as a principal software architect, senior refactoring engineer, and independent code auditor.

Your task is to inspect this entire repository and design a comprehensive, staged process for improving it through appropriate abstraction. The intended result is a codebase in which every meaningful segment is easier to:

- understand;
- audit;
- test;
- maintain;
- change safely;
- reuse where genuinely appropriate;
- replace independently;
- reason about without relying on hidden context.

This is an investigation and planning task, not an implementation task.

OPERATING CONSTRAINTS

1. Do not modify application source code.
2. Do not perform refactors.
3. Do not commit, push, create branches, open pull requests, or alter repository history.
4. Do not install packages or change dependencies.
5. You may run safe, non-destructive inspection commands and existing tests, builds, linters, type-checkers, dependency analysers, or coverage tools.
6. Do not suppress, repair, or work around existing failures merely to obtain cleaner results.
7. You may create or overwrite only this report file:

    CODEBASE_ABSTRACTION_AND_AUDITABILITY_PLAN.md

8. Record any limitations that prevented inspection. Never silently skip an area.
9. Preserve existing behaviour as the default assumption. Recommend behavioural changes only when clearly identified and justified.
10. Do not assume that more abstraction is always better. Identify over-abstraction, unnecessary indirection, and premature generalisation as problems too.

PRIMARY OBJECTIVE

Produce an evidence-based process for incrementally improving the architecture and internal organisation of the whole repository.

The process must cover all meaningful repository areas, not merely the most prominent application code. It must make omissions visible through an explicit coverage ledger.

The final recommendations should improve:

- separation of concerns;
- module cohesion;
- dependency direction;
- explicit contracts and interfaces;
- naming and discoverability;
- isolation of side effects;
- management of state;
- testability;
- error handling;
- input validation;
- observability;
- security reviewability;
- configuration handling;
- documentation;
- appropriate reuse;
- ability to make small, independently reviewable changes.

DEFINITION OF “ABSTRACTION”

Treat abstraction as the creation or improvement of meaningful boundaries around stable responsibilities.

Good abstractions should generally:

- represent a coherent concept;
- hide implementation details that callers should not need;
- expose a small and explicit contract;
- have clear ownership;
- have limited and understandable dependencies;
- reduce duplication without obscuring behaviour;
- make testing and replacement easier;
- reduce the amount of code a reviewer must understand at once.

Do not recommend abstraction merely to reduce line count.

Explicitly identify cases where the better solution is:

- clearer inline code;
- deleting unused code;
- consolidating duplicate implementations;
- splitting an oversized unit;
- removing an unnecessary wrapper;
- replacing inheritance with composition;
- reducing generic parameters;
- making an implicit dependency explicit;
- retaining some duplication because the concepts are likely to diverge;
- leaving working code unchanged.

DEFINITION OF “AUDITABLE”

Treat a segment as auditable when a reviewer can efficiently determine:

- what it is responsible for;
- what inputs it accepts;
- what outputs or side effects it produces;
- what assumptions and invariants it relies on;
- which dependencies it uses;
- how failures are represented;
- which security or privacy boundaries it crosses;
- where it is called from;
- how its behaviour is verified;
- whether a proposed change is safe.

DEFINITION OF “REUSABLE”

Treat reuse as justified only when:

- the same concept occurs in multiple places;
- those occurrences share genuinely stable semantics;
- the proposed abstraction has a clear owner and contract;
- reuse will reduce total maintenance cost;
- consumers will not become coupled to unrelated behaviour.

Do not create speculative frameworks for hypothetical future consumers.

REQUIRED INVESTIGATION METHOD

Use multiple passes. Do not jump directly from a superficial scan to recommendations.

- README files;
- CONTRIBUTING documentation;

- development documentation;
- package or workspace manifests;
- coding standards;
- CI configuration;

State which instructions governed your analysis.

Establish a machine-derived inventory of the repository.

Prefer tracked-file information such as `git ls-files`, supplemented where appropriate by filesystem inspection.

Account for every tracked file by assigning it to one of these categories:

- production source;
- user interface;
- server or backend;
- shared library;

- configuration;
- infrastructure or deployment;

PASS 8 — DESIGN A STAGED IMPROVEMENT PROCESS

Create a sequence of small, reviewable refactoring waves.

The process should generally follow this safety order:

1. establish a reliable baseline;
2. add or strengthen characterisation tests around risky behaviour;
3. document existing contracts and invariants;
4. remove clearly dead code;
5. improve naming and local clarity;
6. isolate side effects and external integrations;
7. untangle dependency cycles;
8. separate mixed responsibilities;
9. consolidate proven duplication;
10. introduce justified reusable abstractions;
11. migrate consumers incrementally;
12. remove obsolete paths;
13. validate the resulting architecture;
14. encode architectural rules in tooling and repository guidance.

Adapt that order where repository evidence justifies doing so.

For each wave provide:

- objective;
- included segment IDs;
- exact paths or components affected;
- prerequisite work;
- recommended change;
- behaviour that must remain unchanged;
- tests needed before work begins;
- validation after the change;
- likely risks;
- rollback or recovery approach;
- suggested maximum change size;
- review focus;
- completion criteria;
- dependencies on earlier or later waves.

Avoid large “rewrite this subsystem” recommendations. Break large changes into independently mergeable steps.

PASS 9 — DEFINE AUDITABILITY STANDARDS

- one clear primary responsibility;

- controlled side effects;
- documented invariants;
- predictable error contracts;
- clear security and trust boundaries;
- meaningful names;
- limited size and complexity;
- appropriate tests;
- traceability from public behaviour to implementation;
- absence of surprising global state;
- limited dependency fan-in and fan-out;
- reviewable change scope.

Make the checklist specific enough to use during pull-request review.

PASS 10 — DEFINE ABSTRACTION DECISION RULES

Create a decision framework for determining whether to extract an abstraction.

Include questions such as:

- Is the concept genuinely the same in all candidate locations?
- Is it likely to change for the same reason?
- Can its contract be stated clearly?
- Does extraction reduce the context required to understand callers?
- Does it reduce coupling rather than move it?
- Can it be tested independently?
- Is there evidence of at least two real consumers?
- Would duplication be safer than coupling the consumers?
- Is the proposed interface smaller and more stable than its implementation?
- Will callers need flags, type checks, or exceptions to use it?
- Is the abstraction named after a domain concept rather than an implementation accident?

Include explicit warning signs for premature or harmful abstraction.

QUALITY REQUIREMENTS

- Be exhaustive in coverage but concise within each finding.
- Prioritise evidence over architectural fashion.
- Reference concrete paths and symbols.
- Distinguish confirmed facts from inference.
- Label confidence as high, medium, or low.
- State uncertainty rather than filling gaps with assumptions.
- Distinguish necessary abstraction from optional cleanup.
- Include positive findings so that good existing design is preserved.
- Do not recommend a repository-wide rewrite.
- Do not propose changing everything merely for consistency.
- Do not treat all duplication as a defect.
- Do not optimise solely for reduced line count.
- Do not propose interfaces that merely mirror one implementation.
- Do not use vague recommendations such as “improve modularity” without specifying where, why, and how.
- Make the proposed process safe for incremental execution by another engineer or agent.
- Ensure each recommendation can be traced to repository evidence and at least one segment ID.
